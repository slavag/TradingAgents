# Current Model Catalog and Three-Role Discovery

## Purpose and scope

Refresh the models offered by every provider this fork supports, and make the suggestions useful for its three existing runtime roles: **quick analysis**, **deep reasoning**, and **verifier/reflection/final report**. This is model-selection guidance for the TradingAgents workflow, not a claim that any model has demonstrated superior investment returns. Do not introduce per-agent model configuration or silently switch an existing run to a new model.

The shared catalog currently feeds CLI menus, web menus, strict-provider validation, capability controls, and role defaults. The web picker exposes fewer providers than the backend factory. A model-list refresh must keep those consumers consistent. The previous run records and user configuration remain unchanged.

## Catalog and recommendation policy

Maintain one curated catalog for each provider key accepted by the existing client factory, including distinct international/China keys. It contains only text/chat models suitable for this workflow; image, audio, embeddings, moderation, and managed-agent-only IDs do not enter the selectable list. Each current entry records its exact API ID, lifecycle (`current`, `preview`, or `legacy`), official source URL, and the date it was checked. Provider-specific custom/deployment IDs stay available through a clearly labeled custom entry. Legacy IDs remain accepted for reading and explicitly configured runs, but are neither first-choice suggestions nor misrepresented as current.

The same catalog produces role-specific ordered suggestions in CLI and web. Quick favors latency/cost with working tool calls; deep favors reasoning and adequate context for debate and Portfolio Manager work; verifier favors reliable structured output, grounded synthesis, and manageable cost. Display a short rationale and lifecycle label rather than unsupported superlatives or hard-coded prices. A model is suggested only when its API surface can support the role's tool/structured-output requirements; a newly discovered but unverified model may be selectable with a caution, never labeled recommended. Promoted defaults and explicit user/environment selections take precedence. Do not silently change the selected model when recommendations or live discovery update; show a configured model missing from current discovery as retained but unverified.

The refresh is anchored to official documentation checked on 2026-10-13, including [OpenAI models](https://developers.openai.com/api/docs/models), [Claude models](https://platform.claude.com/docs/en/models/overview), [Gemini models](https://ai.google.dev/gemini-api/docs/models), [Grok models](https://docs.x.ai/developers/models), [DeepSeek models](https://api-docs.deepseek.com/quick_start/pricing/), [Meta Model API models](https://dev.meta.ai/docs/models), [Alibaba Model Studio](https://help.aliyun.com/zh/model-studio/model-list-text-generation/), and each remaining provider's official catalog. Current examples include `gpt-6.1-sol`, `claude-sonnet-5-5`, `gemini-3.8-flash`, `grok-4.7`, `deepseek-flash`, `qwen3.8-flash`, and `muse-spark-1.3`; these are catalog candidates, not automatic defaults. Meta's `muse-wonder-1.0` is preview-only, and Contributor-mode Muse IDs must be explicit opt-ins because of their data-use difference.

## On-demand discovery

Provide an explicit **Refresh available models** action in web and CLI. It performs only read-only model-list requests and never invokes a model for inference. The server/local CLI obtains credentials from the existing `PROVIDER_API_KEY_ENV` mapping and uses fixed, provider-owned discovery endpoints; credentials, prompts, model responses, and raw provider error bodies never enter returned JSON or logs. Use a short timeout, bounded response size and model count, and a short in-process cache with a visible freshness timestamp. A missing key, unauthorized response, timeout, malformed payload, or provider outage leaves the curated/custom choices usable and returns a bounded warning code.

Initial discovery adapters cover providers with verified listing APIs: OpenAI, Anthropic, Google, xAI, DeepSeek, Meta, OpenRouter, Mistral, Groq, and loopback-only Ollama. The provider-specific response parser filters non-chat modalities and keeps exact IDs. For the remaining provider keys, keep curated/custom choices until their listing API and response metadata have been verified against official docs; do not guess a compatible `/models` endpoint. Azure deployment names, Bedrock account/region IDs, generic OpenAI-compatible URLs, and non-loopback Ollama hosts are not probed from a browser-supplied URL. They retain manual/custom entry. Discovery does not run at page load, analysis start, or batch processing.

The web endpoint accepts only a known provider key, never a caller-supplied URL. It enforces a fixed host allowlist, HTTPS for hosted providers, no cross-host redirects, and loopback-only HTTP for local Ollama. The UI merges discovered models beneath curated recommendations, preserves the current selection even when absent from the live list, and distinguishes `recommended`, `available in this account`, `legacy`, `preview`, and `custom`. A refresh for one role/provider must not mutate the other roles.

## Compatibility and testing

Keep the existing `get_model_options`, `get_role_model_options`, `get_web_model_options`, `get_known_models`, and `get_model_capabilities` contracts or provide explicit compatibility adapters. Reconcile model IDs with the OpenAI-compatible capability table, provider parameter gates, prompt-cache rules, default configuration, CLI/provider menus, and the web payload validator. Do not change pinned/promoted selections or historical records. Expose all backend-supported provider keys in the web picker, including region variants, only after verifying the factory and credential mapping accepts them.

Test the curated provider/role matrix against exact documented IDs and lifecycle labels; CLI/web/validator parity; live-response filtering; pagination where documented; selection preservation; auth/timeout/malformed/oversize fallbacks; no secret leakage; fixed-host/redirect/loopback boundaries; and no model invocation during discovery. Use stubbed HTTP/SDK responses, not paid API calls. Run the full test suite, scoped Ruff, and `git diff --check`. Keep changes uncommitted unless separately authorized.
